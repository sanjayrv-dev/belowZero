# Pitch deck and live demo

Give the pitch lead five minutes for the deck and three minutes at the machine. Put the Windows build, commit, device model, interface and capture date on the evidence slide. Use measured values only. Until the team runs the experiment, every result below is a branch in the script.

## Ten slides

1. **The Wear-Leveling Lie.** Hold up a card with a file offset on one side and a NAND page on the other. Ask, “When I overwrite this byte twice, who decides where the second write lands?” Turn the card over. The SSD controller decides.
2. **Where the old bytes went.** Draw file offset → NTFS cluster → host LBA → flash translation layer → NAND. Put a line at the controller. Wei and colleagues found single-file overwrite methods unreliable on their tested SSDs by reading the flash chips. Keep the finding tied to their experiment. [Original FAST ’11 research](https://www.usenix.org/conference/fast11/reliably-erasing-data-flash-based-solid-state-drives)
3. **A decision at the desktop.** Show one synthetic file in the radial drop-zone. Display the volume, eligible byte count and trailing bytes. The same confirmation opens from Explorer. Credit Filee for the interaction inspiration. [Filee project](https://github.com/KnifeLemon/Filee)
4. **What Windows can request.** Animate one file-relative range, then show the OS acknowledgement and the directory-entry outcome as separate fields. Windows allows several subsequent read values, including the original bytes. [Windows TRIM contract](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_file_level_trim)
5. **When the bridge obscures the drive.** Drop a fixture on a USB enclosure. Display the actual ineligibility reason. Open the source to show it survived. Offer a new encrypted workspace for the next document.
6. **Protect a document from its first write.** Show the new VHDX, BitLocker readiness and the first file created inside. Then show its locked state on private reattach. Keep a close-up of these two state readings for the judges.
7. **Who can touch what.** Diagram Explorer/Avalonia, ordinary-user file worker, privileged disk probe and session-owning vault process. Point out that the probe accepts only a volume identity. The ordinary worker retains the file handle.
8. **The experiment.** Put the baseline and post-operation bytes side by side with the tool receipt, image offsets and hashes. Invite a judge to choose the marker. Use the observation branches below.
9. **Users and compliance.** Start with a developer handling temporary client exports. The receipt describes one local action. Organizational media sanitization, backups, retention and erasure obligations require separate controls. Propose an open-source pilot measured by correct routing and comprehensible receipts. [NIST SP 800-88 Rev. 2](https://csrc.nist.gov/pubs/sp/800/88/r2/final)
10. **Next evidence to collect.** Ask for hardware partners and independent reproduction. Publish the tested device/driver matrix, the BitLocker policy matrix and the number of unsupported cases. Show one open question the pilot can resolve.

## The live forensic experiment

**Set the stage.** Engineer 1 prepares an isolated, expendable, directly attached NTFS SSD. Keep OS, swap, tool output, evidence and the hex viewer on another drive. Use an unencrypted test volume for the plaintext readback. Leave production settings on other disks alone. A VM is sufficient for illustrating a logical read, and exercises the virtual-device fallback. Use the physical rig for the direct-device path. Create a small dedicated test volume so that all three captures and hashes fit within the rehearsal time.

1. Create two ordinary, allocated files A and B with identical, page-aligned 1 MiB contents. Put the marker `EMHACKS-<run-id>` at byte zero. Create a third, untouched file with a different control marker. Flush all three. Record each SHA-256, file identity, first-extent VCN/LCN, bytes per cluster and sector, and size. A and B should have identical hashes and distinct locations.
2. Acquire a read-only **raw logical volume image** before the operations. Take all captures from the same volume boundary and write them to separate media. For the first byte on simple NTFS use the independently established cluster-zero base in volume bytes plus first LCN × bytes per cluster. A whole-disk image also needs the partition start. Check all three markers at their own computed offsets before proceeding. A dynamic VHDX file offset is unsuitable for this comparison. Keep a copy of the baseline image, label it, and hash it. [Retrieval pointer layout](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-retrieval_pointers_buffer)
3. **Act 1, the overwrite control.** Select only A in a traditional overwrite tool, for example Sysinternals SDelete in single-file, one-pass mode. Record tool version, chosen mode and exit status. Acquire a fresh volume image. Open its copy read-only in HxD, jump to A’s baseline byte offset, and show a 64-byte window beside the baseline. Verify the untouched control. If the marker survives, it was visible at that logical address at capture time. If it disappears, that observation is valid too. No desktop carver can read controller-private NAND through this interface. [SDelete](https://learn.microsoft.com/en-us/sysinternals/downloads/sdelete) · [HxD](https://mh-nexus.de/en/hxd/)
4. **Act 2, the file hint.** Recheck B's address and marker immediately before the action. Drop B, show the inspected device and planned coverage, confirm once and display the genuine terminal receipt. After the worker closes the handle, capture the volume again. Check the directory outcome, then open the corresponding 64 bytes at **B’s own pre-operation offset** and verify the control again. Use separate, newly opened images for every reading. Record the elapsed interval. Ordinary deletion, block reuse and device processing also influence observations after unlink.
5. **Read the outcome aloud.** For zeros, say “Windows returned zeros at this address in this capture.” For unchanged, mixed or other bytes, show them and give the actual result. For a partial receipt, show the preserved name and flag possible content change. If identity, mapping or the control fails, mark the comparison inconclusive. If the rig fails, switch to a dated rehearsal capture labelled *recorded* or to the published chip experiment labelled *prior research*. Never assign the same logical address to both test files without measuring it.
6. **Vault encore.** Initialize an empty vault, show readiness and expected protector inventory, create a fresh marker *inside*, and close its editor. During a rehearsed close retain the owned image long enough for the session owner to verify a locked, private reattach. Show the recorded lock result and subsequent retirement. If close reports busy, close the application and retry. If policy prevents qualification, demonstrate the blocked state. A locked image tests the access boundary. Permanent loss of every credential copy remains a separate assurance question. [BitLocker lock status](https://learn.microsoft.com/en-us/windows/win32/secprov/getlockstatus-win32-encryptablevolume)

**Evidence to keep.** Save tool versions, before/after image hashes, device topology, geometry, file IDs and offsets, time of each capture, raw 64-byte samples and redacted receipts. In Autopsy, add each raw image as a separate data source. Its file Hex tab uses offsets within the chosen object. Use HxD on the raw volume image for the recorded volume offsets. Keep a still of each validated outcome for the projector. [Autopsy data sources](https://sleuthkit.org/autopsy/docs/user-docs/4.22.0/ds_page.html) · [Autopsy content viewer](https://www.sleuthkit.org/autopsy/docs/user-docs/4.22.1/content_viewer_page.html)

## Judge Q&A

- **“Why build this if Windows already trims?”** Windows already manages storage. The added value is per-file eligibility, an explicit receipt and an encrypted-from-creation workflow for future sensitive work.
- **“Can you detect a lying USB bridge?”** Windows can expose the bus and reported support. The product treats unknown forwarding as ineligible. Moving an existing file into a vault would leave its earlier exposure unresolved.
- **“What about a 300-byte secret?”** Its data may reside in the file record, and it contains no complete page for a file hint. The utility reports that limit and preserves the source.
- **“How fast?”** Report rehearsal median and range for inspection, confirmation-to-receipt and vault initialization separately. Include sample count, file size, CPU, SSD and encryption mode. UAC wait and encryption bring distinct latency. No benchmark has been supplied with this blueprint.
- **“What happens on a crash?”** Partial file disposal can change bytes before unlink. Vault recovery checks durable identities, lock state and open handles. An ambiguous orphan remains available for review.
- **“Is this a NIST purge or GDPR certificate?”** The receipt establishes a bounded action on one host. Any broader determination needs a defined scope, accepted technique and validation evidence. [NIST media sanitization guidance](https://csrc.nist.gov/pubs/sp/800/88/r2/final)
- **“Will SmartScreen trust it?”** Sign and timestamp the installer, executables, DLL and identity package. Show the verified publisher in rehearsal. Reputation and enterprise policies can still affect launch. [Microsoft signing and reputation guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
